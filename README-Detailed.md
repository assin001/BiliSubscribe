# BiliSubscribe · B站订阅（GsCore / 早柚核心）

订阅 B站 UP 主后，插件定时轮询该 UP 的**视频投稿**与**动态**，一有更新就推送到订阅它的群聊。

参考实现：[Lianzy-Baimiao/astrbot_plugin_bililive](https://github.com/Lianzy-Baimiao/astrbot_plugin_bililive)（AstrBot 版本）。

## 安装

把本目录整个放到 GsCore 的插件目录下：

```
gsuid_core/
└── plugins/
    └── BiliSubscribe/          ← 本目录（目录名必须是 BiliSubscribe）
        ├── __init__.py         命令注册 + 轮询引擎（核心只导入这个入口）
        ├── paths.py            插件根目录 / 资源路径（唯一真源）
        ├── ICON.png            控制台插件图标（核心按 plugins/<名>/ICON.png 取，别挪）
        ├── assets/             随插件分发的图
        │   ├── bilihelp.jpg        群聊帮助图（bili帮助 发这张）
        │   └── biliadminhelp.jpg   管理员帮助图（bili管理帮助 发这张）
        ├── fonts/              卡片用的字体（优设标题黑 / 思源黑体 / 霞鹜文楷 / Orbitron）
        ├── bili/               B站接口层（只跟接口/协议打交道，不发消息）
        │   ├── api.py              B站接口（WBI 签名 / buvid 指纹 / 风控退避）
        │   ├── login.py            扫码登录换 Cookie
        │   ├── wbi.py              WBI 签名
        │   ├── dynamic.py          动态解析（纯函数）
        │   └── fulltext.py         长文正文抓取 + 合并转发节点（纯函数为主）
        ├── core/               业务内核（配置 / 数据 / 状态 / 过滤）
        │   ├── config.py           插件配置（Web 控制台配置页 + 本地兜底）
        │   ├── storage.py          订阅数据（数据库优先，JSON 兜底）
        │   ├── models.py           订阅数据表
        │   ├── runtime.py          运行状态（状态卡片用）
        │   ├── pending.py          待定队列
        │   ├── adfilter.py         带货 / 广告过滤
        │   └── games.py            内置游戏白名单（官方号 → 命中栏目才推，每游戏一条）
        └── render/             出图与发送
            ├── card.py             推送卡片渲染（PIL 画图）
            ├── status_card.py      控制台状态卡片
            └── push.py             文案格式化 + 主动推送
```

三条来自核心的硬约束，改目录结构时别踩（都是读 `gsuid_core` 源码确认的）：

1. **目录名必须叫 `BiliSubscribe`**：核心用 `sys._getframe(2)` 取调用方文件路径，再取
   `plugins/` 后面**第一级目录名**当插件名 —— 所以子包拆到多深都认得出，但顶层目录名一改，
   Web 控制台的插件配置页就是空的；
2. **`ICON.png` 不能挪进子目录**：核心的 `plugin_icon_api.py` 硬编码 `plugins/<插件名>/ICON.png`，
   连 `icon.png` 都不认（插件自己那份 `status_card.get_icon()` 才兼容小写，两者是两套查找）；
3. **`pyproject.toml` 留在根目录**：核心加载插件时用它检查依赖。

重启 GsCore（或在 Web 控制台重载插件）后，用 `bili帮助` 检查是否加载成功。

依赖：`aiohttp`（核心自带）+ `qrcode`（扫码登录画二维码，核心一般也自带；
真缺了插件会退回"发登录链接"，功能不中断）。

## 推送卡片

每条更新都会画成**一张卡片图**再发（`render/card.py`，按原设计稿那套模板渲染；
模板是 600px 设计稿，卡片等比放大 1.5 倍到 900px）：

```
┌────────────────────────────────────┐
│ ⬤  异环  [UID 3546636978489848]  ▩ │  头部：头像 + 名字 + UID 胶囊 + 二维码
│    订阅更新                        │  （淡粉底，头像是圆形带白圈）
├────────────────────────────────────┤
│  海特洛特别资讯 | 曳尔沐            │  文章标题 36px 粗体 #222
│  #异环# #异环曳尔沐#               │  标签 24px #0057AE（霞鹜文楷）
│  「你好呀~又见面了，我的朋友~？」   │  引语 27px #444
│  正文……（行高 1.6）https://…      │  正文 24px #222；链接 #7B68EE（Orbitron）
│  ┌─────────────────────────────┐  │  配图铺满宽度、高 450（cover 裁切，圆角 6）
│  └─────────────────────────────┘  │
│  10-04 11:00         BiliSubscribe │  底部 21px #666
└────────────────────────────────────┘
```

**头部（新样式）** 的元素与来源：

| 元素 | 来源 | 拿不到时 |
| --- | --- | --- |
| 圆形头像 | 动态：`module_author.face`；视频：`view.owner.face` | 画一个粉圆 + 名字首字 |
| UP 名 | 动态/视频的作者名 | `未知UP` |
| `UID xxxx` 胶囊 | 作者 UID（动态的 `mid` / 视频的 `owner.mid`） | 不画（名字自然占满） |
| `订阅更新` | 固定文案 | — |
| 右侧二维码 | **原文链接**（动态是 `t.bilibili.com/xxx`，视频是 `www.bilibili.com/video/BV…`） | 不画（名字区域变宽） |

- 二维码是**服务端画的**（Python `qrcode`，插件依赖里已有）：网页那套 QRCode.js 用不上；
  参数一一对应 —— 前景/背景色 → `fill_color`/`back_color`、容错级别 → `error_correction`、
  边距 → `border`、块大小 → `box_size`。缺库/生成失败只是不画那一格，卡片照常出；
- 名字太长会先按"到二维码为止、且扣掉 UID 胶囊宽度"截断加 `…`（不然会把胶囊挤到二维码上）；
- 头部现在是**淡粉底 + 粉色字**（不是原来的重粉白字），UP 名用的是**标题字体**（思源黑体 Bold），
  所以优设标题黑那款字体目前**卡片里没用上**（文件留着不碍事，`header` 角色也还在）。

正文会按模板**拆成三块**分别上色：整行都是 `#标签#` 的 → 蓝色标签块；
以 `「` 开头的 → 引语块；其余 → 正文，正文里的链接单独用蓝紫色画（对应模板的
`<a class="link">`）。正文超过 18 行截断并提示"点链接看全文"。

**字体按角色找**（优先级从高到低：插件目录里的字体 → 系统字体 → 兜底）；仓库里已经
随插件带了这四款字体（放在 `BiliSubscribe/fonts/`，**插件目录下任意子目录都会被扫到**）：

| 角色 | 模板要求的字体 | 随插件带的文件 | 找的关键字 |
| --- | --- | --- | --- |
| 头部 | 优设标题黑 | `YouSheBiaoTiHei-2.ttf` | `YouSheBiaoTiHei`（新头部里 UP 名改用标题字体，这款目前没画到） |
| 标题 | 思源黑体 Bold | `NotoSansSC-VariableFont_wght.ttf`（可变字重，自动取 Bold） | `NotoSansSC[-Bold]` / `SourceHanSansSC` / `msyhbd` |
| 正文/引语 | 思源黑体 | 同上（Regular） | `SourceHanSansSC` / `NotoSansSC` / `xihei` / `simhei` |
| 标签 | 霞鹜文楷 | `LXGWWenKai-Medium.ttf` | `LxgwWenKai` |
| 时间/链接 | Orbitron | `Orbitron-VariableFont_wght.ttf` | `Orbitron` |

- **可变字体**（文件名带 `VariableFont`）会按角色调字重：标题/头部取 Bold、正文 Regular
  （Pillow 支持才行，不支持时退回"同一个字体 + 描 1px 边"）；
- 某角色没找到专用字体时，**跟着正文字体走**（保证整卡同一套字形），再退系统黑体/华文细黑；
- **回退链等价于 CSS 的 `font-family` 列表**：模板里写的
  `font-family: 'LxgwWenKai', 'PingFang SC', sans-serif`，在这边就是
  **角色关键字 → 插件目录 → 系统字体 → 华文细黑/黑体 → 核心字体 → PIL 默认**，逐级往下找；
- 每次启动第一次画卡会把「角色 → 实际用了哪个字体文件」打进日志，
  字体没认上（文件名不匹配、woff2 没转格式）能当场看出来：
  `B站订阅：卡片字体 title → NotoSansSC-VariableFont_wght.ttf（可变字重）`；
- **PIL 读不了 woff2**：模板里引的 `./YouSheBiaoTiHei.woff2` 之类要先转成 ttf/otf/ttc；
- 缺字体不会报错，只是字形降级，不会画不出卡片。

### 字体体积：要不要子集化 / 转 woff2

先分清**发出去的是什么**：卡片是**服务端用 PIL 画好的图**（带封面走 JPEG、纯文字走 PNG），
推给群/移动端的只有这张图——实测纯文字 86KB、带封面 116KB，**超过 300KB 会自动降质量重编**。
**字体文件不会跟着发出去**，所以"字体太大影响移动端"对这套流程不成立；字体体积只影响
仓库/磁盘（现在 4 个文件约 42MB，最大的是霞鹜文楷 24MB）。

- **不要转 woff2**：PIL/FreeType 读不了 woff2，转了只会**静默退回系统字体**，字形直接变掉。
  woff2 是给网页 CSS 用的，服务端画图用不上；
- **不要给正文/标题/标签字体做子集化**：卡片上写的是**动态内容**（UP 名、动态标题、正文、
  话题标签），会用到哪些字事先不知道；子集化后遇到没收录的字就是**空白豆腐块**，比字体大更糟；
- 真要瘦身，按这个顺序：
  1. 换**官方精简版**而不是自己裁——例如霞鹜文楷有 `LxgwWenKaiGB`（国标字集，明显更小），
     文件名里仍带 `LxgwWenKai`，直接替换 `fonts/` 里的文件即可；
  2. 只对**固定文案**用的字体做子集：现在卡片上的固定文案（`订阅更新`、`UID`）用的都是
     正文/标题字体，而它们同时要画动态内容，所以**没有**能安全子集的字体了；
     真要做只能拿"只画这几个字"的那款（比如把 UP 名换回优设标题黑）单独裁；
  3. 字体不进 git（`.gitignore` + 部署时单独放一份），只在服务器上留着。

接下来是链接（单独一条），然后是**其余图片**：

- **≥2 张 → 一条合并转发**（单独另起一帧，内容是"群聊的聊天记录 / 图片 ×N"，
  点开看大图），避免十来张图把群刷一屏；转发构造失败会自动退回一张张发，不会丢图；
- **只有 1 张 → 跟卡片放在同一条消息里**（为一张图单独开个转发不值当）；
- **图片一律按 B站原链接原样发，插件永不拼图**：下载再转码/压缩/拼图只会掉画质
  （拼图功能以前有，已经删掉了），各张图交给平台自己排版更自然；
- 动图**一视同仁**：线上实测动图到群里本来也只显示首帧静态图，所以不再单独给它开路，
  统一进合并转发。`bili修改配置 拼图 开` 现在会直接回一句"该功能已删除"。

**"少发一点"的三条规则**（触发会在转发最后补一句说明，不会让人以为图丢了）：

| 规则 | 阈值 | 说明 |
| --- | --- | --- |
| 单条张数上限 | `MAX_EXTRA_IMAGES = 9` | 卡片放首图，其余最多补 9 张，再多就不发了 |
| 单条动图张数 | `MAX_EXTRA_GIFS = 4` | 其余图里的**动图最多 4 张**，多出来的跳过 |
| 单张大动图 | `EXTRA_GIF_MAX_BYTES = 10MB` | 只查**动图**（HEAD/`Range: bytes=0-0` 拿长度，静态图不查省请求），超了这张不发 |

触发时的提示文案（转发里最后一条，或没有转发时单独发一条）：

```
动态动图触发大小上限规则，部分发送
还有 3 张图超过单条上限（9 张）
还有 5 张动图超过单条上限（4 张）
（完整内容点原文链接看）
```

- 探测大小是**并发**做的（`asyncio.gather`），而且**探不到就不跳图** ——
  只有明确超限才不发，免得又变成"图被吞了"；
- 动图的**下载 + 压缩也是并发**的（`GIF_CONCURRENCY = 4`，用 asyncio 并发而不是真开线程，
  对 aiohttp 下载更合适）：一张张处理一条 7 张动图的动态会拖到适配器掉线。

**多动图的动态会慢**：核心（Sget）发图前会把远程图片**抓下来**再发，一条动态里好几张
7~8MB 的动图就是几十兆的下载 —— 实测日志：7 张动图 → 8.7 秒 → NoneBot2 掉线重连
（队列续发，不会丢消息，但群里看着就是"卡了一下"）。这种情况把
`bili修改配置 动图 开`（`gif_shrink`）打开：>1MB 的动图先压到 ~480px/128 色/最多 30 帧，
**本地只下一次、所有订阅群复用同一份字节**，几十兆降到几兆。

**默认不出全文**：卡片本身就是预览，正文太长会刷屏，要看全文点链接就行。
需要的话 `bili修改配置 全文 开`（`push_full_text`）会让它在卡片之外再补发全文。

**全文永远另起一帧发**（不跟卡片混在一条消息里）。核心的发送逻辑有个坑：同一帧里如果有
node 段，node 展开出来的内容会被排到该帧其它段**前面** —— 表现就是"转发跑到卡片前头、
还只有前几条"。所以插件把全文单独发，靠核心发送队列的 FIFO 保证顺序。

如果转发内容不全，先看核心的 **`EnableForwardMessage`（合并转发消息）**：

- 「允许」→ 收到完整的合并转发（推荐）；
- 设成**数字**（如 `3`）→ 只会发出前 3 段，看起来就是"转发里没有全文"；
- 「全部拆成单独消息」→ 拆成一堆单条消息，也会被当成"顺序乱了"。

不想依赖这个设置的话，把 `bili修改配置 转发 关`（配置项「长文全文用合并转发」）关掉，
插件就把全文**按 ~1500 字并成几条消息**发（5000 字公告 = 4 条，既不刷屏也不依赖转发）。
**这一项默认就是关的** —— 转发在不少核心/适配器上会被截断或拆散。

**转发段数会自动压缩**：平台对合并转发的条数普遍有上限（常见是"只发前 N 条"），
以前固定 500 字一刀，一篇 6000 字的版本公告会切成 **16 段**，于是出现"长文转发看起来失败、
短文正常"。现在按正文长度自动放大每段字数（500 → 最多 2000），把段数压到 8 段左右
（上面那篇公告现在是 10 段，含标题段和原文链接段）。段数**真的超了**（> 10 段）时不再指望
转发：这一次直接改成按段并块发，同时日志留一条 warning —— 宁可不发转发卡片，
也不能让正文缺一段。

相关开关（`bili修改配置` 或控制台）：

| 开关 | 默认 | 作用 |
| --- | --- | --- |
| `推送用卡片图`（`push_card`） | 开 | 关掉就退回"文字 + 图片"的老发法 |
| `带封面图`（`push_cover`） | 开 | 卡片里是否放首图 |
| `补发其余图片`（`push_extra_images`） | 开 | 卡片之外是否补发其余图片（一律原链接原样发） |
| `长文补发全文`（`push_full_text`） | 关 | 开：卡片之外再补发全文（默认只发预览） |
| `长文全文用合并转发`（`full_text_node`） | 关 | 开：全文发成一条合并转发；关：按条并块发 |
| `动图先压小再发`（`gif_shrink`） | 关 | 开：>1MB 的动图先压小再发（**合并转发里的动图也会压**） |
| `推送用短链`（`push_short_link`） | 开 | 卡片下面那条链接发 `https://b23.tv/xxx` 短链（动态 / 投稿 / 专栏都支持；生成失败退回原链接） |

几个实现上的取舍：

- **画不出来就退回文字**：没装 PIL、字体拿不到、封面下载失败都不抛异常，这条自动退回
  "文字 + 最多 3 张图"，推送不会因为画不出卡片而漏；
- **字体按角色找**（见上表）：关键词顺序就是优先级，装了模板里的字体就用它，
  没装就退华文细黑/黑体；插件目录里的字体永远最优先。**PIL 不认 woff2**，要放 ttf/otf/ttc；
- **标题（含头部的 UP 名）只在"没有专用字体"时描 1px 边**（都退回华文细黑这种情况），
  有真正的粗体文件（如雅黑粗体、思源黑体 Bold）就不描，避免过重；
- **链接不进卡片**（画进去也点不了），在卡片下面单独发一条纯链接；
- **配图按模板 fixed 高度**（450px）+ **cover 居中裁切**，所以不同比例的图在卡片里
  高度一致，不会忽高忽低；
- **体积**：带照片的卡片出 JPEG（quality 92），纯文字卡片出 PNG（更小更清晰）；
  整卡最高 4096px，正文超过 18 行截断并提示"点链接看全文"。

## 长文动态（默认只发预览）

版本更新公告这类长文（专栏 / opus 动态）整段塞进一条消息会刷屏，所以**默认只发卡片预览**
（标题 + 摘要 + 封面 + 链接），要看全文点链接。

打开 `bili修改配置 全文 开`（`push_full_text`）后，卡片之外会再补发全文：

```
① 预览：卡片（标题 + 摘要前 14 行 + 首图）+ 链接
② 全文：默认按 ~1500 字并成几条普通消息发（open 合并转发见 full_text_node）
```

- **opus id 和动态 id 是同一个数**（动态点开后的链接就是 `www.bilibili.com/opus/<动态id>`），
  所以没解析出 opus id 时插件会直接拿动态 id 去问，专栏类动态（`cv<号>`）也照样能拿到全文。
- 全文来源五级兜底，任一成功即用：

  | 顺序 | 来源 | 说明 |
  | --- | --- | --- |
  | ① | opus 详情 | `x/polymer/web-dynamic/v1/opus/detail?id=<opus_id>`，段落模型（图文能保序） |
  | ② | 动态详情 | `x/polymer/web-dynamic/v1/detail?id=<动态id>`，有时比 feed 里全 |
  | ③ | opus 页面 | `www.bilibili.com/opus/<动态id>`，服务端渲染、正文直出；按 F12 看到的两种结构解析：长文在 `div.opus-module-content / opus-paragraph-children` 里，普通动态整页只有一个 `<p>`（正文）+ 后面的配图 |
  | ④ | 老专栏正文 | `x/article/view?id=<cv号>`，返回 HTML，转成文本+图片 |
  | ⑤ | 专栏页面 | `www.bilibili.com/read/cv<号>/`，从 `__INITIAL_STATE__` 或 `read-article-holder` 里抠 |

  页面解析统一走"找正文容器（`opus-module-content` / `opus-paragraph-children` / `read-article-holder`）
  → 没有就取那个 `<p>` + 它后面的图"，图片同时认 `src` 和懒加载的 `data-src`。

- 四级都失败就**只发预览**（预览里本来就有原文链接），不会因为抓不到全文而漏推。
- 合并转发怎么落地由核心的 `EnableForwardMessage` 配置决定（平台不支持合并转发时可以
  选择拆成多条或禁止），插件侧只负责构造 node。
- 正文上限 `full_text_limit`（默认 5000 字），超出截断并在结尾提示看原文；
  每个转发节点最多 500 字，正文图片最多 6 张。
- **多图动态**：卡片放首图，其余图按原链接一张张发（不拼图、不转码）——
  详见下面的「推送卡片」。开关：`push_extra_images`。
- 白名单外的长文进了待定队列时：**入队时就把全文抓好存下来**，点「可以推送」时直接
  带上全文，不会再抓一次。
- 调试用 `bili测试全文 <动态链接|动态ID|cv号>`，会告诉你命中哪一级、抓到多少字、配图几张。

**实机验证**（拿《异环》1.4 公告 `www.bilibili.com/opus/1251145718800842753` 实测）：

- `opus/detail?id=<动态id>` **免登录就能返回正文**，这条公告是 183 个段落的段落模型
  （`module_content.paragraphs`，全是 `TEXT_NODE_TYPE_WORD`）→ 一级兜底就够用；
- 该动态的 **opus id 就等于动态 id**（`1251145718800842753`），页面标题里的
  「编号 cv53144750」是它对应的专栏号；
- 真实返回里 `modules` 是**列表**（`[{module_type: MODULE_TYPE_TITLE}, …
  {MODULE_TYPE_CONTENT, module_content: {paragraphs: [...]}}]`），不是字典 ——
  解析已按列表形态兼容（早期版本会在这里报 `'list' object has no attribute 'get'`）；
- 这条公告**没有内联配图**（头图在预览里），正文里的图会以段落 pic 节点出现，
  插件会把它们按原位放进合并转发；
- 页面兜底也实测可用：不依赖 `__INITIAL_STATE__`，直接按
  `div.opus-module-content / opus-paragraph-children` 容器抠，能拿到 3000+ 字。

## 图片链接的格式

页面里同一张图会给出两份地址（`<picture>` 结构）：

```html
<picture class="b-img__inner">
  <source type="image/webp" srcset="//i1.hdslb.com/bfs/new_dyn/x.jpg@264w_264h_1e_1c.webp">
  <img src="//i1.hdslb.com/bfs/new_dyn/x.jpg@264w_264h_1e_1c.avif" loading="lazy">
</picture>
```

插件统一这样处理（`normalize_image_url`）——**原则是尽量原样发，只做必要的最小改动**：

- `<source>` 的 `srcset` 优先于同块的 `<img src>`；两者归并成一张图，不会重复发；
- 只把 `@参数.avif` 的渲染后缀换成 `.jpg`（avif 客户端基本发不出来，而且它一定是静态图）；
- **`.gif` 和 `.webp` 一律不动**：B站的动图就是这两种（可能是一张 7.8MB 的动图 webp），
  任何转码都可能让"动的图"变成"静态图"（早期把 `@….webp` 改成 `.jpg` 就踩过这个坑）；
- 非 B站 CDN 的链接不动；`data:` 占位不算图；懒加载同时认 `src` 和 `data-src`；
- 接口来的图（动态 feed / opus 段落里的 pic 节点）走同一套归一化，所以两边发出来的图一致。

## 动态过滤（白名单）

游戏官方号（比如异环 `3546636978489848`）的动态里混着大量推广、联动、抽奖，绝大多数
是群里不想看的。所以这里不是"人工审核"，而是**白名单过滤**：

> **订阅了某游戏的官方号，它的非视频动态就按该游戏的白名单过滤**；
> 命中白名单栏目才推群，其余直接过滤掉；投稿视频照常自动推送。

```
新动态 ──► 命中该游戏的白名单栏目？ ──是──► 直接推群
              │否
              └──► 默认：过滤掉（不推群、不通知）
                   开了「未命中的动态进待定队列」才会：
                   进队列（落盘，重启不丢）──► 通知到指定会话（带图）
                      可以推送 <编号> ──► 推送到所有订阅群
                      bili跳过 <编号> ──► 丢弃（只留记录）
                      不作处理 ────────► 不推（超 7 天自动过期）
```

所以默认**零操作**：`bili订阅 3546636978489848` 就完事了（订阅回复会提示
"这是《异环》官方号，动态按白名单过滤"）。看内置了哪些游戏、白名单里有哪些栏目：
`bili过滤规则`。**排查"这条怎么没推"用 `bili过滤测试 <链接>`**：它只判断不发送，会打出
标题/正文、命中哪个栏目、最终判定；判定 ❌ 就说明要被过滤，把栏目名加进 `core/games.py`
或 `bili白名单` 即可。目前只有异环：

| 游戏 | 官方号 | 白名单栏目（命中即推） | 其它动态 |
| --- | --- | --- | --- |
| 异环 | 异环（`3546636978489848`） | 活动日历、角色档案、前瞻回顾、更新公告、海特洛特别资讯、海特洛衣橱、限定棋盘、弧盘研募计划 | 过滤 |

想看被过滤掉的都长什么样、顺手捞几条回来，就打开待定队列（默认关）：

```
bili修改配置 待定 开        # 或到 Web 控制台勾「未命中的动态进待定队列」
bili待定 在这里             # 指定通知会话
bili待定                    # 看待定列表（推送：可以推送 3   过滤：bili跳过 3）
bili待定 记录               # 最近的拍板记录
```

### 为什么按游戏写死

各游戏官方号的发帖习惯不一样（有的图文、有的专栏、有的把公告做进图里），该放行哪些
栏目自然也不同。所以规则跟着"游戏"走，写死在 `core/games.py` 里，而不是让你每次
换游戏都去加一遍 UID、还容易漏：

```python
GAMES = {
    "异环": GamePreset(
        name="异环",
        uids={"3546636978489848": "异环"},        # 官方号（可多个）
        pass_keywords=(
            "活动日历", "角色档案", "前瞻回顾", "更新公告",
            "海特洛特别资讯", "海特洛衣橱", "限定棋盘", "弧盘研募计划",
        ),
        note="公告与资讯都发在官方号动态里，图文、专栏、多图混排",
    ),
    # 新增游戏就照抄一条，互不影响：
    # "崩铁": GamePreset(
    #     name="崩铁",
    #     uids={"1340190821": "崩坏星穹铁道"},
    #     pass_keywords=("活动日历", "角色档案"),
    # ),
}
```

关键词取**栏目名本身**，别带尾巴：标题里可能夹书名号/emoji（`「限定棋盘」即将开启`），
而且联动公告也叫 `异环×罗森联动活动即将开启` —— 带「即将开启」会把推广也放行。
匹配范围是**标题 + 正文**，所以 `海特洛特别资讯` 这种写在标题里的栏目同样命中。

发帖方式特殊的游戏（比如公告只发在图片里，得看图里的文案才能判断），给这条预设再挂
一个 `decide` 函数做定制判断，其它游戏完全不受影响：

```python
def decide_xxx(parsed) -> str:
    """返回 PUSH / PENDING / FILTER：直接推 / 交给待定队列 / 明确过滤。"""
    if "抽奖" in (parsed.get("text") or ""):
        return FILTER          # 纯抽奖：连待定都不进
    return PENDING             # 拿不准的按默认口径处理

# uids=…, decide=decide_xxx
```

**额外白名单关键词**（可选，在游戏内置栏目之外再补一层，对所有游戏生效）：

```
bili白名单 情报回顾        # 加一条
bili白名单                 # 看当前列表
bili白名单 取消 情报回顾    # 移除
```

留空不影响内置规则；开了待定队列时，待定项没处理就是"不推"。

设计取舍：

- **只拦非视频动态**：投稿视频（版本 PV 这类）本来就是官方号的主内容，照旧自动推送，
  所以也不会出现"待定捞回来后又跟投稿列表重复推一遍"的问题；
- **没有记录就是不推**：待定项没有任何决定就一直不推，不会过期后补推；
- 待定项落盘在 `data/BiliSubscribe/pending.json`，重启后仍可继续处理；超 7 天或同一个
  UP 攒超 50 条会自动清理（记为"已过期"），避免队列无限长；
- 拍板有历史记录（`bili待定 记录`），最近的 200 条。

## 手动补推一条动态

订阅生效**之前**的历史动态不会自动补推（首次检查只建基线），需要单独发一次时：

```
bili推这条 https://www.bilibili.com/opus/1251145718800842753      # 推到本会话（哪发的推哪）
bili推这条 https://t.bilibili.com/1150000000000000002 订阅群      # 推给订阅了这个 UP 的所有群
bili推这条 cv53144750                                            # cv 号也认
bili推这条 BV19tej6oE3H                                          # 视频（BV号/av号/视频链接）
bili推这条 https://b23.tv/0wyDLI4                                # 短链也认（手机分享复制的那种）
```

- 认这五种参数：动态链接 / 动态ID（`t.bilibili.com/xxx`）、opus 链接（`/opus/xxx`）、
  专栏（`read/cv<号>` / `cv<号>`）、**视频**（`BV<10位>` / `av<号>` / `www.bilibili.com/video/BV…`）、
  **短链**（`b23.tv/xxx`，先跟一遍 302 跳转换成真实链接再认；手机分享文本
  「【标题】 https://b23.tv/xxx」整段贴进来也行，会自动挑出链接那段）；
- **视频走投稿那条路**（`x/web-interface/view`，不需要 WBI 签名、基本不吃风控）：
  同样是一张卡片（标题 + 时长 + 简介 + 封面），`订阅群` 模式按视频作者 UID 找群；
- 长文照样**预览 + 合并转发全文**，多图动态照样把多余的图放进转发；
- 走「订阅群」时用动态里的作者 UID 定位订阅群；只给 cv 号时作者从专栏接口取，
  取不到会提示改用本会话推送；
- 补推**不改游标**，也不会污染去重记录（该条以后如果有更新，轮询照常处理）。

### 只给链接时，内容是从哪来的

三条路**依次**试，任一条拿到东西就用，全拿不到才会出现"空壳卡"：

| 顺序 | 来源 | 说明 |
| --- | --- | --- |
| ① | 动态详情接口 `x/polymer/web-dynamic/v1/detail` | 最快，但**经常整片 `-352` 风控** |
| ② | **opus 页面** `www.bilibili.com/opus/<id>` | 服务端渲染、正文直出，最稳；标题/作者/正文/配图/时间都在 `__INITIAL_STATE__.detail` 里 |
| ③ | 文章形态 + `fulltext` 多级兜底 | 只给 cv 号时走这条 |

踩过的两个坑，现在都修好了：

1. **页面里的 `modules` 是列表**（`[{module_title}, {module_author}, {module_content}]`），
   而接口给的是按模块名索引的 dict —— 解析器只认 dict，页面数据一进来就 `AttributeError`，
   于是就"什么都解析不出来"。现在 `_modules()` 两种形态都收口；
2. **卡片是先画、正文是后抓的**：`build_dynamic_msgs` 拿 `parsed` 现画卡片，而标题/作者/
   正文是 `fulltext` 抓的过程中才回填进去的，顺序反了就画成
   「未知UP · 投稿了文章」+ 空白正文的空壳卡。现在手动补推会**先把内容补齐再画卡**
   （`fulltext.fill(parsed, force=True)`），实在什么都没有才在正文位置写一句
   "没能取到正文，点链接看原文"，不再发空白卡。

顺带对齐了段落解析和页面所见：`para_type 2` 的**段落级图片**、`para_type 6` 的
**链接卡片**、以及话题/表情/@ 这类 RICH 节点的 **`rich.text`**（以前只认
`TEXT_NODE_TYPE_WORD`，结果 `#异环#` 这种话题整段丢）。

## 扫码登录

`bili登录`（管理员）发一张二维码，用哔哩哔哩手机客户端扫一下，Cookie 自动写进配置：

1. `passport.bilibili.com/x/passport-login/web/qrcode/generate` 取 `url` + `qrcode_key`；
2. 用 `qrcode` 把 `url` 画成 PNG 发到群里（缺库时只发链接，手机浏览器也能登）；
3. 后台任务每 2 秒轮询 `.../qrcode/poll`：

   - `code == 0` 成功，Cookie 从响应的 `Set-Cookie` 里取（兜底解析 `data.url` 的 query）；
   - `86038` 二维码失效；`86090`（已扫码待确认）/ `86101`（未扫码）继续等；
   - 有效期约 3 分钟，超时会提示重来；

4. 拿到 Cookie 先用 `nav` 接口校验，**校验通过才写配置**，顺手清掉风控静默期；
5. 轮询在后台任务里跑完再回报，不占住核心的命令队列；同一时间只允许一轮登录。

只保留 `SESSDATA` / `bili_jct` / `DedeUserID` / `DedeUserID__ckMd5` 四个键
（`buvid` 指纹插件每次自己补，不存）。Cookie 是账号凭证，建议用小号扫。

## 配置

配置文件由核心配置体系管理，位于 `gsuid_core/data/BiliSubscribe/config.json`（放在 data 目录，插件更新不会丢）。

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `bilibili_cookie` | 空 | 登录 Cookie，动态接口 -636 / 投稿接口 -352 风控时需要 |
| `check_interval` | 300 | 轮询间隔（秒），最小 60 |
| `sleep_mode` | true | 定时休眠开关：休眠时段内不轮询（手动 `bili检查更新` 不受影响） |
| `sleep_range` | `01:00-07:30` | 休眠时段，`HH:MM-HH:MM`（支持跨天如 `23:30-07:00`；填错按不休眠处理） |
| `cache_ttl_days` | 15 | 图片缓存天数：头像这类重复图同一个 URL 只下一次，到期自动清理 |
| `max_uid_per_round` | 20 | 单轮检查的 UP 数上限（订阅多时轮流查） |
| `max_push_per_round` | 5 | 单轮每个 UP 最多补推几条动态 |
| `notify_video` | true | 推送投稿视频 |
| `notify_dynamic` | true | 推送图文/专栏/转发等动态 |
| `notify_live` | false | 推送直播相关：动态流里的开播卡片 **＋ 真正的开播提醒**（打开后每个 UP 每轮多一次直播间接口请求） |
| `ad_filter` | true | 过滤带货/广告动态（**只对非官方号**；官方号走白名单，不重复过滤） |
| `check_video_list` | true | 额外用投稿列表接口查视频（补动态接口的漏） |
| `push_cover` | true | 推送时带封面图（卡片里的首图） |
| `push_card` | true | 把每条更新画成一张卡片图（头部+标题+正文+首图） |
| `push_short_link` | true | 卡片下面的链接发 `b23.tv` 短链（动态/投稿/专栏；失败退回原链接） |
| `push_extra_images` | true | 卡片之外补发其余图片（一律原链接原样发，不拼图不转码） |
| `push_at_all` | false | 全局 @全体成员 |
| `push_full_text` | false | 长文是否在卡片之外补发全文（**默认关**，只发预览） |
| `full_text_node` | false | 全文用合并转发发；关则按 ~1500 字并块发 |
| `gif_shrink` | false | 动图先压小再发（默认关，原链接原样发） |
| `full_text_limit` | 5000 | 全文最多放多少字，超出截断 |
| `auto_push_keywords` | `[]` | 额外白名单关键词：命中就直接推（各游戏自带的白名单栏目见 `core/games.py`） |
| `queue_unmatched` | false | 没命中白名单的动态是否进待定队列（默认直接过滤） |
| `review_targets` | `[]` | 待定通知发到哪些会话，如 `["qq:group:123456"]` |

`bili修改配置` 支持的项名：`间隔`、`上限`、`动态上限`、`视频`、`动态`、`直播`、`封面`、`卡片`、`全文`（长文补不补全文）、`转发`（全文用不用合并转发）、`动图`（动图要不要先压小）、`at全体`、`投稿列表`、`待定`（`待定 开` 打开待定队列）、`休眠`、`休眠时段`（`休眠时段 23:30-07:00`）、`缓存`（缓存天数）。

   `bili配置` 会显示当前用的是哪个后端。

## 状态卡片

插件启动时会用 `gsuid_core.status.plugin_status.register_status` 注册一张状态卡片，
内容由核心的 `draw_status()`（**状态图 / `信息`、`状态` 命令输出的那张图**）渲染，
顺序即下表顺序：

| 顺序 | 状态项 | 值 |
| --- | --- | --- |
| 1 | 订阅UP | 已订阅的 UP 数 |
| 2 | 订阅群 | 订阅落在多少个群 |
| 3 | 上次检查 | `刚刚` / `5分前` / `2时前` / `未检查` |
| 4 | 已过滤 | 本次启动以来被白名单过滤掉的动态数 |
| 5 | 待定 | 待定队列里还没处理的动态数 |
| 5 | 本轮更新 | 上一轮有更新的 UP 数 |
| 6 | 累计推送 | 本次启动以来推送的消息条数 |
| 7 | 轮询间隔 | 当前间隔（如 `300秒`） |
| 8 | Cookie | `已配置` / `未配置` |
| 9 | 运行状态 | `检查中` / `空闲` |

两点是核心渲染的硬约束，改这里的时候别踩：

- `draw_plugins_status()` 每个插件**最多画 3 个徽章**（源码里 `if indexj >= 2: break`），
  所以 订阅UP / 订阅群 / 上次检查 放在最前面；
- 回调必须无参异步、返回值只能是 `str` / `int` / `float` 且要短：核心会对非数字值调
  `.isdigit()`，返回 `None` 会直接抛 `AttributeError`，徽章也只有 240px 宽。

图标取插件目录下的 `ICON.png`，**注意 Linux 上大小写敏感**，写成 `icon.png`
核心的控制台插件卡片就认不出来（插件本身两种都认，会依次找 `ICON.png` / `icon.png`）；
没有图标文件时用代码现场画一个 B站粉圆角方块 + 白色播放三角（不留二进制文件在仓库里）。
图标任何尺寸都行，核心会缩放到 `128x128`。

## 每条订阅单独设（bili设置）

开关是**按群、按 UP 存的**：同一个 UP，A 群只想收视频、B 群只想收动态都是合法需求。

```
bili设置 异环                 # 看这条现在怎么推
bili设置 异环 关视频 开直播    # 只收动态+直播
bili设置 3546636978489848 全开 动态@全体
```

| 设置项 | 说明 |
| --- | --- |
| `开动态` / `关动态` | 这类动态推不推（图文/专栏/转发…） |
| `开视频` / `关视频` | 投稿视频（含投稿列表查到的）推不推 |
| `开直播` / `关直播` | 开播提醒推不推（还需要管理员开总开关 `notify_live`） |
| `全开` / `全关` | 三类一起 |
| `动态@全体` / `视频@全体` / `直播@全体` | 按类 @全体（`取消动态@全体` 这样取消） |
| `@全体` / `取消@全体` | 三类都@ / 都不@（老的 `bili订阅 <UID> at` 也是这个） |

默认是**全开、不@全体**，所以老订阅升级后行为不变；`bili列表` 里会顺手标出非默认的
（例如 `仅动态/视频｜@全体：直播`）。

## 开播提醒

`notify_live` 打开后，除了动态流里的开播卡片，还会**真去查直播间状态**：

- 数据来自 `room/v1/Room/getRoomInfoOld?mid=<uid>` —— **不需要 Cookie、不用 WBI 签名**
  （带 `live_room` 的 `x/space/wbi/acc/info` 动不动就 `-352`，只当备胎）；
- `live_status`：`0` 未开播 / `1` 直播中 / `2` 轮播；**`0` 或 `2` → `1` 才推**；
- **首轮只建基线**（订阅时他正好在播也不砸一条），之后开始盯着；
- 只在"真有群要直播"时才查（全局关着 = 零额外请求），开播卡片带封面、直播间标题、
  头像和指向直播间的二维码；
- 没开过直播的 UP 拿不到房间号，每轮都会重新问一次（有人开播就会认出来）。

## 带货/广告过滤

只对**非官方号**生效（官方号走 `core/games.py` 的白名单，已经足够严，不重复过滤）。
开关：`ad_filter`（默认开，`bili修改配置 广告 关`）。

规则**故意定得很窄**，宁可漏掉广告也不能误杀正常动态：

| 判据 | 例子 |
| --- | --- |
| B站自己的商品类型字段（结构字段，几乎不会误判） | `additional.type` 含 `goods` |
| 只有带货才会说的词 | 到手价 / 优惠券 / 领券 / 满减 / 下单 / 抢购 / 销量补贴 / 购物车 / 加购 / 橱窗 / 带货 / 小红书 … |
| 明确的电商域名 | `item.taobao.com` / `detail.tmall.com` / `item.jd.com` / `yangkeduo.com` / `jinritemai.com` / `mall.bilibili.com` |

**故意避开**常见词（推荐、收藏、链接、价格、限时、活动…）——那些在正常动态里满地都是，
收进来会把版本公告、攻略、活动预告全误杀。每次过滤都会在日志里写明原因
（`判定为带货/广告（含「到手价」），这条不推`），觉得误杀了就直接关掉。

## 数据存储

订阅数据存进 **GsCore 的数据库**（表名 `BiliSubscribeSub`，一行 = 一个「群 × UP」），
控制台「数据库管理」页里的 **「B站订阅」** 就是它：

> 光定义模型**不会**出现在那个页面 —— 还要在 `core/models.py` 里写一个继承
> `gsuid_core.webconsole.mount_app.GsAdminModel`、带 `@site.register_admin` 的 Admin 类，
> 并用 `model = BiliSubscribeSub` 指过去（`label='B站订阅'`，`icon='fa fa-rss'`）。
> 装饰器是在 import 时执行的，所以这段必须在插件加载必然 import 到的模块里 ——
> `core/models.py` 由 `core/storage.py` 在加载时导入，符合条件。
> 核心没有 `webconsole.mount_app`（版本较老/离线）时只记一条 info 日志，不影响订阅功能。
>
> 排查用：`bili配置` 最后一行「订阅数据」会告诉你当前是数据库还是本地 JSON、
> 以及有没有挂上控制台。以后给表加列，记得同时往
> `gsuid_core.utils.database.startup` 的 `exec_list` 里加 `ALTER TABLE … ADD COLUMN …`，
> 否则老库不会自动补列。

| 列 | 说明 |
| --- | --- |
| `uid` | UP 的 UID（索引） |
| `group_id` | 群号（索引） |
| `bot_id` / `bot_self_id` | 推送用哪个 bot（订阅时所在的那个，不在线才回退到其它在线 bot） |
| `at_all` | 这个订阅是否 @全体成员 |
| `name` | UP 名字（轮询时自动补） |
| `last_dynamic` | 动态游标（按数值比较，不是字符串） |
| `last_video` | 最近一次见到的投稿 BV 号 |
| `pushed_av` | 已推过的 BV 号（JSON 数组），避免动态与投稿列表重复推 |

两点实现说明：

- 游标按 UID 冗余在每一行里（同一个 UP 的游标对所有群是同一份），更新时按 uid
  一次改掉所有行 —— 单表、无 JOIN，取消订阅就是删一行；
- 建表走核心的 `SQLModel.metadata`：核心启动时会 `create_all` 一次，插件里再兜底
  `checkfirst` 建一次（只建自己这张表），所以热重载/手动装插件的场景也不会缺表。

**JSON 兜底**：核心版本较老、装不到 `sqlmodel` 时，自动落
`data/BiliSubscribe/subscribe.json`（结构同上，`groups` 是字典）。首次切到数据库时，
如果表是空的而 `subscribe.json` 里有数据，会**一次性导进去**（表非空则不导、不覆盖）。

**读写一致性**（这块踩过两次，都是"库里明明有、列表却说没有"）：

1. **读不拿"建表成功"标记当前提**。以前读之前先看这个标记，它是假就直接读本地 JSON ——
   于是只要建表那一步失败过一次（哪怕数据库里数据好好的、控制台也能看到），
   列表就会一直说"本群还没有订阅"。现在只要后端是数据库就**直接去问数据库**，
   读不通才退本地 JSON；
2. **写库失败兜底进 JSON 的，读要能看见并补写回库**。写库瞬时失败（SQLite 写闸门
   超时那类）会兜底写本地 JSON，读的时候把这份并进来（`_json_pending` 标记），
   并**逐行补写回数据库**，补完清标记 —— 免得"刚订阅成功 → 紧接着取消/列表说本群没有订阅"。
   数据库里已有的行永远以数据库为准，已删的订阅不会被 JSON 残留复活。

`bili配置` 的「订阅数据」两行、以及 `bili列表` 空列表时的输出，都是给这类问题定位用的：
会打**本群群号**、当前数据源、**数据库 / 本地 JSON 各几个 UP**，还有"其它群共 N 条"的提示 ——
一眼能看出是"这个群真没订"还是"数据源没读全"；读库失败时还会带上**具体报错**。

**读全表三级兜底**：不同核心版本给的方法不一样，按实测顺序逐个试 ——
`select_rows()`（不带条件 = 全表，最稳）→ `get_all_data()`（文档里的方法，但**有的版本会抛**，
线上就遇到过"`bili订阅` 能认出已订阅、`bili列表` 却说读不到"）→ 自己用 `async_maker`
开 session 查。三种都不行才退本地 JSON。

**待定队列**单独放 `data/BiliSubscribe/pending.json`（待定项 + 最近 200 条处理记录），
它跟数据库后端无关，两个后端都用它 —— 待定数据量小、只在管理员侧流转。
（老版本的 `review.json` 会在首次加载时自动改名过来。）

推送行为：

- **首次检查只建立基线**，不会把历史动态/投稿刷一屏；单轮最多补推 `max_push_per_round` 条。
- 轮询只更新游标与名字字段，读改写有锁、且与命令操作分离，运行期间用户改订阅不会被覆盖。

## 已知限制

- B站接口有风控：动态接口不带 Cookie 时可能返回 `-636`，投稿列表接口可能返回 `-352`。
  吃到 `HTTP 412` 后插件会静默 5 分钟再试。**强烈建议配置 Cookie**。
- 直播开播提醒依赖 `room/v1/Room/getRoomInfoOld`（不需要 Cookie）；如果哪天这个接口没了，
  开播提醒会静默失效（动态流里的开播卡片不受影响）。
- 广告过滤是"规则制"（结构字段 + 窄词表 + 电商域名），**不是模型判别**：新型带货话术
  可能漏过；它只对非官方号生效，官方号仍走白名单。
- 静音时段（休眠）只影响自动轮询，手动 `bili检查更新` 不受影响。

## 自测

插件本体不带测试文件。想自己验一遍时，最小做法是在 `gsuid_core/plugins/` 下起一个
装了本插件的 GsCore，用管理员发：

```
bili帮助            看是否加载成功（发得出来帮助图就是加载了）
bili检查更新        立刻跑一轮，看日志里有没有动态推送 / 过滤记录
bili过滤规则        确认内置白名单（异环的官方号与栏目）
bili推这条 <链接>   手动推一条，验证发送链路
```
